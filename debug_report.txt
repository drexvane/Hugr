FINDING #1: ANTHROPIC_BASE_URL Environment Variable Not Honored
----------------------------------------------------------------
The codebase does NOT reference ANTHROPIC_BASE_URL anywhere. The AnthropicModel 
class in client.py (line 104-119) instantiates the Anthropic SDK client with 
only api_key parameter:

  self._client = Anthropic(api_key=resolved)

The Anthropic SDK's constructor accepts a base_url parameter to override the 
endpoint, but this code does not pass it. If ANTHROPIC_BASE_URL is set in the 
environment (e.g., to https://api.xkiro.com), it will be IGNORED.

IMPACT:
Once the DuckDB fix lands and the catalog loads, any LLM-dependent query will 
fail at the network layer if:
- The environment has ANTHROPIC_BASE_URL=https://api.xkiro.com
- The proxy serves OpenAI-style schema that the Anthropic SDK doesn't expect
- OR the Anthropic SDK ignores the env var entirely (which it currently does)

WORKAROUND:
The agent has a --stub mode that uses KeywordModel (no network call). This 
works without a fix but is limited to keyword matching.

PROPER FIX:
Modify AnthropicModel.__init__ to honor ANTHROPIC_BASE_URL:

  base_url = os.environ.get('ANTHROPIC_BASE_URL')
  self._client = Anthropic(api_key=resolved, base_url=base_url) if base_url 
                 else Anthropic(api_key=resolved)

FINDING #2: Multiple DuckDB Ingestion Sites Need Same Fix
----------------------------------------------------------
The recommended fix sites in the original report miss ONE additional code path
that performs the same CREATE TABLE ... AS SELECT * FROM df pattern:

1. Warehouse.from_tables() at warehouse.py:123
   - Used for multi-table uploads
   - Iterates over tables dict and creates each with same pattern:
     con.execute(f"CREATE TABLE {_ident(name)} AS SELECT * FROM df")

The snapshot loader is NOT in the same blast radius. The function at
warehouse.py:211 is `open_warehouse`, and it attaches Parquet files as
DuckDB views via `con.execute(_view_sql(table.table, target / table.file))` -
DuckDB reads them directly in its native type system. There is no pandas
DataFrame intermediary and no `CREATE TABLE ... AS SELECT * FROM df` to fail.
The catalog discovery inside `open_warehouse` does call `.fetchdf()` on a
LIMIT 1000 sample, but that DataFrame is only used for pure-Python inspection
by `discover_schema()`; it is not pushed back into DuckDB. So the snapshot
loader is not affected by the StringDtype bug.

The real exposure surface for this bug is therefore exactly two call sites:
`from_df` and `from_tables`. Both must be patched.

KNOWN FOLLOW-UP (not in this fix's scope):
The helper below only handles `include=['string']` (Arrow-backed StringDtype).
pandas 3.x can also emit nullable extension types - `Int64`, `Float64`,
`boolean` - for columns with missing values. The current sample CSVs do not
contain any, and the ecommerce default loads cleanly with string-only
normalization. If a real uploaded CSV later surfaces a
`NotImplementedError: Data type 'Int64' not recognized` (or similar), extend
`_normalize_for_duckdb` to include them in the same `select_dtypes` call. Do
NOT add that scope pre-emptively: pandas 3.x's behaviour around nullable
dtypes changes between point releases, and a wider net can mask regressions
in the discovery path.

BLAST RADIUS COMPARISON:

Option 1 (Fix in ingest.py):
  ✓ Fixes user CSV upload path
  ✗ Does NOT fix default dataset bootstrap in server.py:78
  ✗ Does NOT fix from_tables() multi-file path
  Scope: Narrow - only ingest.load_file_as_df()

Option 2 (Fix in warehouse.py - both methods) - RECOMMENDED:
  ✓ Fixes from_df() at line 100 (default dataset bootstrap in server.py:78)
  ✓ Fixes from_tables() at line 123 (multi-file upload path)
  ✗ Does NOT need to touch the snapshot loader - different code path
  Scope: Complete for the actual bug

RECOMMENDED APPROACH:
Create a helper function in warehouse.py that normalizes DataFrame dtypes
before any CREATE TABLE operation:

  def _normalize_for_duckdb(df: pd.DataFrame) -> pd.DataFrame:
      """Convert pandas StringDtype to object dtype for DuckDB compatibility.

      DuckDB does not recognize pandas' native StringDtype (pd.StringDtype()).
      This converts string columns to object dtype, which DuckDB treats as
      VARCHAR. Only string columns are touched; numeric and boolean columns
      pass through unchanged.
      """
      df = df.copy()
      for col in df.select_dtypes(include=['string']).columns:
          df[col] = df[col].astype('object')
      return df

Then call it in:
- from_df() before line 100
- from_tables() before line 123

FINDING #3: Frontend JSON Parse Error Handling is Fragile
----------------------------------------------------------
Location: web/app.js lines 194-196, 293-296, 497-499

Current pattern in fetchStatus():
  const res = await fetch('/api/status');
  if (!res.ok) throw new Error('Failed to fetch status');
  const data = await res.json();

Problem: The code calls res.json() BEFORE checking res.ok. When the server 
returns a 500 with text/plain body "Internal Server Error", the browser 
attempts to parse it as JSON and throws:

  "Unexpected token 'I', "Internal S"... is not valid JSON"

This obscures the actual error. The catch block sees a JSON parse error, not 
the real 500 status.

CORRECT PATTERN:
  const res = await fetch('/api/status');
  if (!res.ok) {
      const text = await res.text();
      throw new Error(text || res.statusText);
  }
  const data = await res.json();

This ensures:
- Non-OK responses are read as text first
- The actual error message reaches the user
- JSON parsing only happens on successful responses
- Future 500s surface as readable errors, not parse exceptions

Affected locations in app.js:
- Line 194-196: fetchStatus()
- Line 293-296: executeAnalysis() 
- Line 497-499: handleUpload()
